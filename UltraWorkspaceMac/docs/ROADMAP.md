# Deckhand — roadmap, ideas & strategy

Deckhand is an independent, native client for the UltraBar X (CoreBar + QuantumLink modules). The vendor's own software is thin, especially on macOS, so Deckhand aims to be the client people actually use. This doc captures the plan and the open questions; it is a living document.

## Status today (works)

- Discovery (UDP :5319), pairing (TLS :7431, tap-Approve, trust-on-first-use cert pinning), token stored in a protected file (no Keychain prompt).
- Live bus scan + provisioning (SET_GATEWAY_CONFIG 30300) with an on-disk module cache that keeps asleep modules (e.g. the DotKey) from being dropped.
- Push cards to a VivoCube (RGB565 + tar/gzip over HTTP :8080). Seven cube cards since 2026-11-03: weather (weather only, no clock), music, Claude Code monitor, crypto (up to five coins, one card each), calendar, date, picture. The live readings (CPU, network, battery, storage, disk I/O, top CPU, uptime) and clocks (clock, world clock) were removed from the cube library — a picture refreshed every 5 minutes at most cannot be a live feed; the bar draws its own live cards.
- **VivoCube switching = the vendor's own model (DONE)**: all listed cards (max 6) are rendered into one multi-layer package (layer n → widget 100+n), uploaded once, given 10 s to be applied by the module, and then switched every interval by writing property 9 = `(layer<<16)|widget` — no flash rewrite per step; contents are re-uploaded only every 5 minutes at most, and only when the pictures changed (2026-11-04). Images are opaque RGB565 by default (alpha is opt-in; the vendor encoder uses straight alpha, ours is premultiplied). A **Fix black screen** button (screen on + layer 1/widget 101, after reading the cached properties 4 and 9) handles the "black cube" case the CoreBar's property cache can produce. Cube Wi-Fi: **Set cube Wi-Fi…** writes property 7; before each upload Deckhand re-writes it while the cube reports "connecting" (property 6 = 3), which completes the join (hardware 2026-11-03).
- Per-device screens (VivoCube cards + switching; CoreBar page with the bar's own cards — the CoreBar rotation idea was retired 2026-11-03), live on-screen card preview, wire-log, About, MIT license.
- CoreBar big-screen: the one-shot preview (PREVIEW_SCREENSAVER 30742) turned out to be **broken in the firmware** (BadTokenException — see PROTOCOL.md); removed from the UI. Replaced by **CoreBar pages**: the page list (30710), **Publish page** (1108, confirmed only when pages from the official app would be lost, superset of the standard page) and page switching (1103). **Confirmed on hardware 2026-11-01**: the Deckhand page renders our cover on the clock card. Done since: hourly cover refresh (re-upload repaints via ReloadProfileEvent), the Deckhand page as the bar's start page (`isDefault`, re-selected on every connect), the bar's own cards on the page (WEATHER, WORLD_TIME, all five SenseCube cards, Mac stats, buttons) and one **Open \<app\>** (`APPS`) card per installed app — APPS cards confirmed on hardware 2026-11-03. Still open: a cover picker per page.
- The mock CoreBar answers the vendor's `discovery.ultrabar` probe, emulates the property 4/9 cache (including the black-screen case) and captures every upload to `mock-corebar/captures/`, so the official app can be run against it.
- **Library pages (2026-11-04)**: Installed (everything in use on the bar and the screens, update and remove, Update all), and Widgets, Apps and Screensavers each as a list + detail with an Installed / On-the-cube / On-the-page switch and the item's settings. Marketplace apps and screensavers are installed, updated and removed through the bar's own app store (30600, the bar downloads the package); Deckhand's eleven bar apps over Wi-Fi ADB. Settings → Debug bridge shows the ADB state and can turn Wi-Fi ADB on over USB and keep it on after reboots.

## Near-term (next)

- **CoreBar big screen — design pivot after the vendor-client analysis**: there is **no wallpaper and no full-screen image page**. A profile is a strip of fixed-size vendor cards (clock, weather, world time, timer, PC-control buttons, scenes, module cards, system stats…), and the only place for our own image is the **TIME card's cover** (`icon`, ≈540×240 card with a blurred copy behind it). So the plan became: Deckhand pages = vendor widgets configured from the Mac (schemas are fully known, see PROTOCOL.md) + our rendered image as the clock cover, written with BATCH_SAVE_PROFILE (1108) and switched with 1103 — built and on hardware. Policy as built: the card list lives in Deckhand's settings, the `SCENE_DEPENDS_PROFILE` (30710) id list is read before every write and shown under *Pages on the bar*, the device's `"default"` profile is always re-sent with an empty TIME icon so the user's on-device choice survives, assets go only under `subDir=deckhand`, and the publish asks for confirmation when pages made in the official app would be lost (**the vendor app's Deploy wipes Deckhand's assets and profiles** — the page says so). There is no full-screen output at all (30742 is broken).
- **Wide widget layouts** are therefore clock-cover sized (roughly square to 5:1, small), not 1424×280 strips; the "iStat-style status strip" idea maps onto the vendor's CPU/MEMORY/STORAGE/NETWORK cards, which are fed by PUSH_MESSAGE queries the Mac must answer (see inputs below).
- **VivoCube panel size — RESOLVED 2026-11-01 (hardware test)**: the panel is **240 × 240**. A 240 px test pattern fills the glass edge to edge and a 280 px one is not shown; the apparent margin in photos is the thick bezel. 240 px is both the vendor's 100 % icon size and the physical resolution, so `canvasSize` stays 240.
- **SenseCube** (DONE for the readable sensors): temperature, humidity and ambient light are polled over the protocol (deviceId 11/12/10, propertyId 1; app scales temp/hum ÷10) and shown live on the SenseCube page. Presence (mmWave), sound level and vibration are **event-only on the device and not exposed over :7431** — they drive on-device widgets/scenes only; since 2026-11-03 all five readings (temperature, humidity, light, presence, sound level) can go on the CoreBar page as the bar's own `SENSE_CUBE_*` cards (the light/presence/sound cards are not yet verified on the glass). Possible future path: the Home Assistant entity bridge.
- **DotKey / KnobKey input** (DONE with fixed bindings — see *Device-first* below; a per-key action editor is the open part): the device does NOT push raw key/knob events. You bind a control to a "PC" target in the active profile's module config — KnobKey rotation → a `PC_VOLUME`/`PC_BRIGHT` device from the 1617 tree, DotKey key → a `PC_CONTROL` action (hot-keys are typed by the CoreBar itself over USB-HID and never reach the Mac). The device then sends `PUSH_MESSAGE` (1000000) **requests** (`SET_VOLUME`, `GET_VOLUME` every 5 s, `PC_CONTROL {action, params}`, `CPU/MEMORY/STORAGE/NETWORK` stat queries) that the Mac **must answer** with the same id. Both halves exist now: the 1108 write path (Publish page) and the **persistent `CoreBarLink` with a heartbeat (act 20 every 3 s) and a PUSH_MESSAGE reply loop** next to the one-connection-per-operation requests.
- **Presence → wake the displays** (HaloBar-style): use the SenseCube's mmWave presence to wake the CoreBar screen + VivoCube on motion (and sleep when away). Presence is event-only on the device and is NOT sent to the Mac, so this must be an **on-device automation** (scene: presence → screen-on / dismiss screensaver), like a HaloBar reacting by itself. Findings: the **presence trigger IS settable over the protocol** (an AUTO scene via `BATCH_CREATE_SCENE` 30500, trigger `DEVICE_STATE state UNOCCUPIED→OCCUPIED`), but there is **no clean "screen-on" action** — `START_SCREEN` is dead; only `BRIGHT` (brightness) and `ACTIVITY` (launch an app, which likely dismisses the screensaver) are available, so "wake" must be approximated and tested on hardware. Scene writes full-replace the list (client owns it), so this waits on the safe profile/scene-write infrastructure.
- **Device settings — reality check**: the :7431 channel is **not** a general settings API. Only **screensaver** (BASE_SET: enable/disable + idle time; the screensaver itself is a separate APK, discoverable with `GET_APP_LIST "SCREENSAVER"`, and a custom slideshow is unlikely without analysing that APK), **screensaver preview**, **gateway config**, **reboot**, **Wi-Fi scan/list** (no connect), **module OTA** (30400/30401, fully specified) and **screen on/off + layer** (per VivoCube) are controllable. Volume, brightness, Bluetooth, Wi-Fi connect, timezone/24h, locale and wallpaper are **on-device only** — moving them into the app would need new vendor firmware. So "only the bare minimum on the device" isn't fully achievable today; we will expose what the protocol allows and surface the rest as device-only. Today the app offers, under Maintenance on the VivoCube page, Cube screen on/off, Fix black screen, Send test picture, Restart cube and Restart bar launcher (ADB) and Set cube Wi-Fi…; the Screensavers page reads and writes the screensaver setting; the Settings page lists time/timezone, Wi-Fi and Bluetooth as device-side, and what the protocol cannot do goes through Android's debug bridge instead (Settings → Bar screen for the presence-aware screen, Settings → Debug bridge for Wi-Fi ADB itself — the page-reselect "keep awake" of 2026-11-03 was dropped because a page switch does not wake a dozing screen).
- **Co-existence with the vendor app**: the vendor client never reads anything back and rewrites the whole device on every Deploy (30300 → 1108 → 1010 → 30500 → `/upload/zip` without `subDir` → 1103). Whichever client deploys last wins; Deckhand must detect it (30710 id set changed, assets gone) and re-apply rather than try to merge.

## Widget marketplace

Goal: let anyone build and share widgets; start as a simple GitHub-based registry, grow into a curated marketplace.

- Phase 1 (GitHub): a public repo (or a folder here) holding community widgets as self-contained bundles + a `registry.json` index. Deckhand fetches the index and lets users install a widget. Curation via PRs.
- Phase 2: an in-app browser (install/update/rate), signing/verification of bundles, and a hosted index.
- See WIDGETS.md for the widget format and the key open decision (how to make a widget run on both macOS and Windows).

## Cross-platform (macOS + Windows)

If there's a business case, a Windows client should follow — ideally "build a widget once, runs on both". That pushes the widget format toward something platform-neutral (see WIDGETS.md). The UltraBar protocol itself is already platform-neutral (TCP/TLS + HTTP), so the device layer ports cleanly; the UI and the widget runtime are the platform-specific parts.

## Business model (first assessment)

Many UltraBar X buyers — macOS users especially — can't do much with the device today, so there is a real, underserved audience and goodwill to capture. Options, roughly in order of friction:

1. **Free / open-source core, donations** — fastest trust, lowest revenue. Good for adoption and to become "the" client.
2. **Freemium app** — core free; a one-time "Pro" unlock or small subscription for advanced widgets (Claude/crypto/calendar/multi-page bar), automations, and the settings suite. Precedent: iStat Menus, Bartender are paid and successful.
3. **Marketplace revenue share** — paid community widgets with a cut, like the Stream Deck store. Needs volume + the Phase-2 marketplace.
4. **Cross-platform Pro** — one license covering macOS + Windows.

Risks/unknowns: the vendor ("Sanytron") could ship or object; trademark (hence the Deckhand rename); the install base size; App Store vs. direct (direct with a Developer ID and notarization since 0.2.0; a paid release would still need a store or a licensing scheme). Recommendation: ship a great free client now to win the users, add a low-friction Pro tier once the feature set (bar pages + settings + input bindings) lands, and keep the marketplace free at first to seed content.

## Decisions (2026-11-01)

1. **Widget format** — web, **TypeScript-first** (HTML/CSS/JS authored in TS, rendered headlessly to an image). Cross-platform by design. See WIDGETS.md for the full option comparison.
2. **Business model** — agreed: free, strong core now → freemium Pro later → marketplace free to start.
3. **Windows** — design for it **from day 1** (shared, platform-neutral core: protocol + widget runtime), even though macOS is the only target we can test here. A second engineer may help on Windows (see COLLAB.md).
4. **Settings in the app** — move everything the protocol allows into the app; keep **Wi-Fi / network onboarding on the device** (and note the protocol can't set most system settings anyway — see the settings reality-check above). Also: make the **physical connection + which USB port to use** unmistakable in-app (the vendor's port design is dangerous — wrong port can fry the mainboard).
5. **Distribution** — **GitHub Releases** with a DMG + full download. Signed with a **Developer ID** and notarized since v0.2.0 (2026-11-04), so there is no Gatekeeper warning; only the first prerelease (v0.1.0) was ad-hoc-signed. See RELEASING.md.

## Connection model (for reference)

Deckhand talks to the CoreBar **over the network** (UDP/TLS/HTTP on the LAN) — there is no USB data transport in the protocol. USB-C is for **power** (and the vendor's HID path). So the "how do I connect" choice is really Wi-Fi vs. wired LAN (most reliable if the device is reachable that way); the USB cable just keeps it powered. Port safety (from the device manual): the CoreBar's **PC-LINK** port is **5 V-only** → connect it to the Mac/computer USB (safe, correct); the **USB-OTG** port is for charging (PD/QC/12 V). **Never** put a PD fast-charger into PC-LINK — it can permanently damage the board. Deckhand surfaces this prominently in-app.

## Device-first (decided 2026-11-01, implemented 2026-11-02 night)

Principle: the CoreBar renders and keeps its own cards alive; the Mac only configures the device and supplies Mac-only data. Consequences and status:

- **Persistent link ("Mac agent")** — `UltraBarKit/CoreBarLink.swift` + `AppModel+Link.swift`: one authenticated connection per selected CoreBar, vendor heartbeat `{"act":20,"id":n}` every 3 s, answers `PUSH_MESSAGE` queries: CPU/MEMORY/STORAGE (percent), NETWORK (cumulative bytes), GET/SET_VOLUME (Mac output volume via osascript), GET/SET_BRIGHTNESS (stub, like the vendor's Mac client), PC_CONTROL (`{"deckhand": next|previous|mute|music.*|page.*}` and the vendor `{action: openBrowser|openFile|startApp}`; `inputText`/`execCmd` are never executed). Link state is the `CoreBarLink.State` enum (stopped / connecting / connected / reconnecting), shown in the device strip. DONE; metric replies confirmed on hardware 2026-11-02 (the bar asks only while a page with those cards is on screen).
- **Deckhand page = device cards** — TIME (our cover), the CoreBar's own WEATHER (needs an AccuWeather key, paid after the trial), WORLD_TIME (Mac timezone as `GMT±H:MM`), SENSE_CUBE_TEMP/HUM/ALS/RADAR/AUDIO, CPU/MEMORY/STORAGE/NETWORK (fed over the link), PC_CONTROL button cards ("Next cube card", "Play / pause") with Deckhand-drawn icons, and one APPS card per installed app. Selectable per card on the CoreBar page and in Widgets. DONE; Deckhand page, Mac cards, APPS cards and all five SenseCube cards seen on the hardware (2026-11-03, launcher 1.0.9).
- **Module bindings in the profile** — KnobKey: turns = Mac volume (PC_VOLUME), button = play/pause in Music (was mute until 2026-11-04); DotKey: button 1 = previous cube card, button 2 = next card (via the Mac), button 3 only answers a hold; the on-device `VIVO_CUBE_TOGGLE` jump-to-card-N binding was dropped 2026-11-04 because it reads as "always the first card"), long-press = standard page. DONE (fixed bindings; editor still open).
- **VivoCube rotation** stays a Mac timer (the firmware has no time/interval trigger — CONFIRMED absent; see docs/research/device-first-findings.md §D), but each step is a single property-9 write and DotKey buttons switch widgets without the Mac.
- **Cover** — the clock-card cover is a static picture (weather & date, no time), so it is refreshed once an hour and at launch instead of every minute; the live time comes from the CoreBar's own TIME card.
- **Plugin packs** — vendor hotkey packs (`config.json` + icons; see docs/research/vendor-plugins-findings.md) are importable as HOT_KEY_GROUP cards; importer not built yet.
- **Monitor app + presence screen** (2026-11-04): `android/DeckhandMonitor` kiosk WebView + `MonitorServer` (:7432) + beacon (UDP 5320); presence-aware screen timeout over ADB (`AppModel+Presence`). Grown the same day into the eleven bar apps below, installed from the Apps page over Wi-Fi ADB (Settings → Debug bridge shows and fixes the ADB state); the beacon only arrives as a unicast (the bar's Wi-Fi drops broadcasts), and since 1.6 the apps load nothing but private-LAN http URLs and never navigate off that host. Still to verify on hardware: the wake/sleep timing of the presence screen.
- **KnobKey turn → Mac volume via CoreAudio (DONE 2026-11-04)**: the bar's own log explained the lag — its `PcVolumeDeviceController` logged "get volume timeout" on every GET_VOLUME because Deckhand's `osascript` answer took 250–600 ms (on the main thread), and it asked again at once, ~120 times a minute. `MacAudio` now caches the default output device's main volume (`'vmvc'`, what the menu-bar slider moves) with CoreAudio property listeners, answers GET_VOLUME from the cache and sets SET_VOLUME through CoreAudio; the turn is bound to PC_VOLUME again. Verified on the Mac Studio: the KEF Coda W is the default output device and reads/sets the same value as AppleScript. Still to confirm on hardware with the knob in hand: the poll rate dropping to the vendor's 5 s and the level following the turn.
- **Five more bar apps (2026-11-04)**: Flights (adsb.lol + adsbdb, a radar on a dark OpenStreetMap map the Mac fetches and caches, up to four flights with route; polled every 10 s while the page is open, every 2 min otherwise), Sun & Moon (`SkyMath`: Meeus/NOAA, checked against timeanddate to the minute), Headlines (CNN from lite.cnn.com — its RSS feeds are dead — plus five RSS sources: BBC, NYT, Guardian, NOS, NU.nl), Verse (bible-api.com, WEB, fixed list by day of year) and Tasks (Linear GraphQL, key in a user-only Store file; tap an issue on the bar and press Done to close it — the page POSTs with the `X-Deckhand: action` header, then the list is re-fetched). Bar apps are 1.7 / versionCode 8, with launcher icons built on Microsoft Fluent Emoji 3D renders (MIT; `android/DeckhandMonitor/tools/fluent/SOURCES.md`). Not built, with reasons: Facebook and WhatsApp (no API for personal accounts), Teams (postponed), Codex/Gemini monitor (no session files on this Mac to build against; planned as one "AI monitor" app with Claude), Aqara cameras (Video Doorbell G4 and Camera E1: no RTSP; the only local route is go2rtc as HomeKit controller, which means unpairing them from Apple Home — the user keeps them in Apple Home, so: not built, decided 2026-11-04), Netatmo (needs a developer app + OAuth, to do once the user has the client id).
- **Deckhand at 30 % CPU, link starved (FIXED 2026-11-04)**: `ClaudeUsage.snapshot()` re-read every transcript touched today (hundreds of MB) every 2 s for the Claude bar app; that kept the Swift thread pool busy, so the link's answers waited (GET_VOLUME p90 1.2 s) and the window went unresponsive. The tally is incremental now (per-file offset, chunked reads, only lines stamped today) and runs at utility priority: 3 % CPU, GET_VOLUME median 1 ms.
- **Cube uploads stop after ~100 of them (FOUND 2026-11-04)**: a leak in the bar's launcher (one network callback per `/upload`, Android caps 100 per app — PROTOCOL.md, upload table). Deckhand now classifies the bare `{"state":-1}` reply, restarts the launcher over Wi-Fi ADB and sends once more, uploads only when the pictures changed, and retries a failed refresh no sooner than the next refresh interval (it used to retry every tick). **Restart bar launcher** is also a button under VivoCube → Maintenance.
- Open hardware checks: KnobKey volume; DotKey layer switching; PC_CONTROL cards push; WORLD_TIME offset format renders; iconScale 80 looks right; SenseCube Light / Presence / Sound level cards. Done: metric cards show live values (2026-11-02), APPS cards show the apps' icons (2026-11-03).
