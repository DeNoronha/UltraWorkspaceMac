# VivoCube image/layer protocol — findings (2026-11-01)

Sources used: decompiled LineOS launcher (`lineos-src/sources/com/ultrabar/launch/...` and the bundled QLink SDK `lineos-src/sources/quantum/link/product/vivocube/*`), the official macOS client `UltraWorkSpace.app` V1.0.1.0 (arm64 slice, `nm` + `otool -tV`, full dump in `scratchpad/uws-arm64.asm`, strings in `scratchpad/uws-strings-hex.txt`), the weather-tool .NET source our encoder was ported from (`scratchpad/ultrabar-weather/src/.../DeviceImage.cs`), vendor docs in `docs/the vendor's support pages/HARDWARE-MODULES.md`, and the two hardware photos (`img_1369.jpg`, `img_1370.jpg`). Scratch extracts of the relevant disassembled functions are in `scratchpad/fn-*.asm`. The "VivoCube_V2_20260728_ota.bin" linked from the vendor docs was fetched to `scratchpad/vivocube-fw/`; it is a 24 KB `UBX-OTA-FILE` STM32 HID blob with no LVGL/`com_res` strings, so it is NOT the display firmware and gave no resolution data.

## Executive summary

What we got right (CONFIRMED by the official client's own encoder, `UM::PixmapToLVGLBinUtils::pixmapToLVGLBin`): the `.bin` format (8-byte header = LVGL v8 `lv_img_header_t` + 4-byte data size, RGB565 big-endian per pixel, optional alpha byte), the tgz layout (`com_res<widgetId>/default.bin`, `pressed.bin`, `config.json`), the `config.json` shape `{"defaultLayer":L,"layers":[{"id":L,"items":[{"type":1,"id":W}]}]}`, the upload URL and the meaning of `"state":200,"data":""`.

What we got wrong or did not know:

1. The 240×240 image is an **icon inside a button widget**, not a framebuffer. The official client has exactly one deployable widget type (`type` 1 = Button); there is no background/full-screen item type, and `config.json` items carry only `type` and `id` (no x/y/w/h/scale). The icon's on-screen size is baked into the bitmap: the client scales the user's icon to `iconScalePercent`% of **240 px** (default 60 % → 144 px, max 100 % → 240 px), keeps aspect ratio, trims transparent borders first, and renders `pressed.bin` at 0.8×. So the firmware's icon canvas maxes out at 240 px; a 240×240 image is what the official client itself produces at 100 %. The real panel resolution is NOT in the client or the launcher; given your photo (image ≈ 70 % of the panel width) the panel is most likely larger than 240 px (HYPOTHESIS: 320 or 360 px square, 240/360 = 67 %, 240/320 = 75 %). Nothing in the client prevents sending a bigger bitmap (the header has 11-bit w/h), so the only way to learn the panel size is a hardware test with a larger opaque image.
2. The `"state":200` reply only means the module **acknowledged** the "update config" command (status byte 0) within 5 s; it has not downloaded or applied anything yet. The module then pulls `http://<corebar>:8080/tgz/<serial>.tgz` itself over **Wi-Fi** (not over the magnetic bus) and re-applies the layer config. The official client literally says "Upload succeeded. Please wait for VivoCube to complete update." There is no busy/queue handling on the CoreBar: every upload deletes and rewrites the same `<serial>.tgz` in the CoreBar cache dir, so a second upload while the module is still fetching the previous one hands it a truncated/replaced file.
3. Alpha (`cf` 5) is definitely supported by the firmware: the official client emits it for every icon that has any non-opaque pixel, which is the normal case for PNG icons. Difference to ours: the official encoder uses **straight (non-premultiplied) RGBA** (`QImage::Format_RGBA8888`), we feed premultiplied RGBA. Our black result with marker 5 is therefore not explained by the marker itself; candidates are the premultiplied data or the 3-byte 240×240 payload (172.8 KB) exceeding what the firmware can decode (HYPOTHESIS).
4. The CoreBar **caches** VivoCube property 4 (screen state) and property 9 (layer+widget id) and re-writes them every time the module asks for status (i.e. after every reboot/reconnect). A stale "screen off" or a layer/widget id that no longer exists in the deployed config is re-applied forever; that is a concrete, code-backed mechanism for "black and stays black" that does not involve the images at all.
5. Limits from the client UI: max **6 layers** and max **6 widgets per layer** (the vendor doc's "3 widget slots" is not what the client enforces). Layer and widget ids are ints 1…65535 (property 9 packs them as `(layer<<16)|widget`).
6. Rotation design: the official client deploys all layers once and switches with property 9 / `VIVO_CUBE_TOGGLE`; "upload N layers once, then toggle" is exactly how the product is meant to work and avoids re-flashing the module every 30 s.

What to change in Deckhand: keep the 240 px icon canvas (optionally test larger), keep opaque RGB565 as default, build one multi-layer tgz per rotation set and switch layers with property 9 instead of re-uploading, never trust `state:200` as "applied" (wait and poll), and on any "black" incident read back properties 4 and 9 first.

## A. Resolution, canvas, item types and fields

**Deployed `config.json` shape — CONFIRMED.** `UM::ProjectModuleUseCase::buildVivoCubeExtraConfig` (`uws-arm64.asm` lines 252477-253785, extract in `fn-*.asm` summary) builds `cfg["layers"] = []`; for each project layer it reads `id` (int) and `default` (bool), appends `{"id":<id>,"items":[...]}` and for each widget appends `{"type":<type>,"id":<id>}` (only those two keys: the `operator[]("type")` / `operator[]("id")` + `push_back` sequence at 0x1000fc440-0x1000fc500), sets `cfg["defaultLayer"] = <id of the layer with default==true>` (0x1000fc744), `dump()`s it to `%1/config.json` (0x1000fc7a0), then `ZlibUtils::packDirectoryToTarGz` → `%1.tgz` (0x1000fc840-0x1000fc8a8). There are no `x`, `y`, `w`, `h`, `scale` keys in the deployed file. Deckhand's `DeployPackager.swift:27-30` produces exactly this shape.

**Item `type` — CONFIRMED.** `quantum.link.product.vivocube.VCWidget`: `WIDGET_TYPE_MAIN = 0`, `WIDGET_TYPE_BUTTON = 1`. `QLinkVivoCube.createWidgets()` (lines 159-184 of the decompiled file) walks `extraConfig.dataConfig.layers[].items[]` and creates a `VCWidgetButton` for every item with `type == 1`; anything else is ignored. In the client, `ModuleVivoCubeWidgetEditor` offers radio buttons "Button" (`typeId` 1) and "Toggle" (`typeId` 2) but the Toggle radio is `hide()`-den immediately after creation (0x10010ba9c), and `buildVivoCubeWidgetFile` (0x1000fd140: `cmp w20, #1`) only produces files for type 1, otherwise errors "unknown widget type: %1". So the only deployable item type is 1 = Button (an icon with pressed/unpressed bitmaps and a key event). There is **no full-screen/background item type** in client V1.0.1.0.

**Icon canvas = 240 px, scale baked into the bitmap — CONFIRMED.** `UM::VivoCubeWidgetButton::updateWidgetInfoFromUI` (0x10010d938-0x10010da3c): the raw icon is `QPixmap::scaled(QSize(round(240.0 * percent / 100.0)...), KeepAspectRatio=1, Smooth=1)` (double constants 0x4059000000000000 = 100.0 and 0x406e000000000000 = 240.0), then a second `scaled` by 0.8 (0x3fe999999999999a) produces the pressed icon; both are stored under db keys `rawIcon`, `unpressedIcon`, `pressedIcon`. `initUIFromRawBaseConfig` reads `iconScalePercent` with default **60** (`mov w20, #0x3c` at 0x10010d474) and clamps 10…100 in `VivoCubeImageEditor::setScaledIconPixmap` (0x10010f450-0x10010f460). `UIHelper::trimPixmapTransparentBorder(pixmap, 2)` is applied to the raw icon before scaling (0x10010f378, 0x10010d51c). `buildVivoCubeWidgetButtonFile` (0x1000fd4d0) then loads `iconUnpressed` / `iconPressed` from the project DB and writes `pixmapToLVGLBin()` of each to `%1/default.bin` / `%1/pressed.bin`.

**The client's preview is a 120 px square "screen" inside a 160 px "screenPanel"** (`VivoCubeImageEditor::createLeftPanel`: `setFixedSize(0xa0,0xa0)` for `screenPanel`, `setFixedSize(0x78,0x78)` for `screen` and its QLabel; preview icon scaled to percent/100 × 120.0). Stylesheet: `#screenPanel { background:#313232; border:2px solid #4a4d50; border-radius:16px }`, `#screen { background:#1f2123 }` — square, not round. So the official UI models the display as a square whose full width equals a 100 % icon (240 px). It never states the physical resolution.

**Physical resolution — NOT FOUND.** No 240/320/360/390/454/466/480 constant tied to the VivoCube exists in the client other than the 240 icon box and the 120/160 preview boxes; the launcher has no VivoCube rendering code (the module renders itself); the vendor doc says only "2.0" circular AMOLED" (`docs/the vendor's support pages/HARDWARE-MODULES.md:9`, wrong about "circular" — your photos show a square panel). From `img_1369.jpg`/`img_1370.jpg` the VivoCube shows a small dot-matrix glyph (roughly 35-40 % of the panel width) centred on black — consistent with the firmware's own default/placeholder layer, not with our card. HYPOTHESIS: the panel is ≥ 320 px (your "≈70 %" for a 240 px icon fits 360 px = 66.7 % or 320 px = 75 %). Hardware test: push an opaque 320×320 and a 360×360 `default.bin` (same encoder; header fields are 11-bit so nothing in our code needs to change) and see which one fills the panel or gets rejected.

**Limits — CONFIRMED (client-enforced).** `ModuleVivoCubeLayer::onClickAddLayerBtn`: `cmp x8, #0x6` then "Maximum of %1 layer items allowed" with `%1` = 6. `ModuleVivoCubeWidget::onClickAddingItem`: `cmp x8, #0x6` then "Maximum of %1 widget items allowed" with `%1` = 6. So 6 layers × 6 widgets in V1.0.1.0 (the doc's "3 widget slots" is outdated or a firmware layout limit we cannot see). Ids: `VCWidgetMain.writeLayerAndWidgetId` throws unless `1 ≤ layerId ≤ 65535` and `1 ≤ widgetId ≤ 65535`. The client allocates ids via `makeUnusedLayerId()` / `makeUnusedWidgetId()`; the reference deploy's `layer 1 / widget 101` is just a convention.

**Project-side layer/widget JSON (what the official client stores in the module bean's `extraConfig.dataConfig`, and what the CoreBar later receives via the gateway config) — CONFIRMED keys:** layer = `{uniqueId:<shortUuid>, id:<int>, name:<string>, default:<bool>, widgets:[...]}` (`createNewLayer`, 0x100113c7c-0x100113e04); widget = `{uniqueId, id:<int>, name:"Widget %1", type:1, icon:<db path>, iconScalePercent:<int>, iconUnpressed:<db path>, iconPressed:<db path>}` (`makeEmptyWidget` 0x10010ad80-0x10010af14, `updateWidgetInfoFromUI` 0x10010db84-0x10010de08). `extraConfig` also carries `netConfig:{ssid,password}` for the module's Wi-Fi (`buildVivoCubeExtraConfig` 0x1000fbc70-0x1000fbe20). The CoreBar uses `dataConfig` only to instantiate `VCWidgetButton` objects so that button key events for those widget ids are dispatched (`QLinkVivoCube.createWidgets`, `dispatchMessage` → "widget not found, widgetId:%s" otherwise). It is not pushed to the module.

## B. Exact `.bin` format

`UM::PixmapToLVGLBinUtils::pixmapToLVGLBin(QPixmap const&)` at 0x1000fde48 (`scratchpad/fn-pixmapToLVGLBin.asm`) — CONFIRMED byte-for-byte:

1. `QPixmap::toImage()` then `convertToFormat(QImage::Format(17))` = `Format_RGBA8888` (straight, non-premultiplied, byte order R,G,B,A in memory).
2. Alpha scan: every pixel's byte 3 compared with 0xFF (0x1000fdf10-0x1000fdf24). Any non-0xFF → `hasAlpha`: bytes-per-pixel 3, `cf` = 5; else bpp 2, `cf` = 4 (0x1000fdf38-0x1000fdf6c). These are LVGL v8 `LV_IMG_CF_TRUE_COLOR` (4) and `LV_IMG_CF_TRUE_COLOR_ALPHA` (5) with `LV_COLOR_DEPTH 16`.
3. Pixel loop (0x1000fdfe8-0x1000fe034 alpha variant, 0x1000fe08c-0x1000fe0c8 opaque): byte 0 = `((R<<8)&0xF800 | (G>>2)<<5) >> 8`, byte 1 = `((G<<3)&0x07E0 | B>>3) & 0xFF`, then (alpha variant) byte 2 = A. That is RGB565 **big-endian (high byte first)**, i.e. LVGL built with `LV_COLOR_16_SWAP = 1`. Row-major, no padding.
4. Header (0x1000fe0e4-0x1000fe150): `w23 = cf | (width << 10) | (height << 21)` as a 32-bit little-endian word (bit layout `cf:5 | always_zero:3 | reserved:2 | w:11 | h:11` = LVGL v8 `lv_img_header_t`), followed by a 32-bit little-endian `data_size` = `width*height*bpp` (taken from the QByteArray size), then the pixel data. Total = 8 + payload.

Deckhand's `DeviceImage.swift:33-52` writes the identical header and identical RGB565 byte order. The one real difference: Deckhand's `rgba(from:)` renders with `premultipliedLast` (`DeviceImage.swift:62`), so in the alpha variant our R,G,B are premultiplied by A while the official bytes are straight. For opaque images this is irrelevant (and `encode(allowAlpha:false)` is the default everywhere in Deckhand: `AppModel+Themes.swift:49,64`, `AppModel+Weather.swift:32`, `AppModel+Music.swift:63`), so **all rotation uploads today are opaque `cf` 4 at 240×240 = 115 200 B + 8 per bin**, same as the weather card that was seen working.

Is `cf` 5 supported for `default.bin`? CONFIRMED yes in the sense that the official client produces `cf` 5 for both `default.bin` and `pressed.bin` whenever the icon has any transparency, and PNG icons with transparent background are the normal input (it even trims the transparent border). Why ours rendered black: NOT determined. HYPOTHESES, in order: (a) we sent premultiplied colour (a semi-transparent/black-background card premultiplied over black is mostly black); (b) at 100 % × 240 px with alpha the payload is 172 808 B — larger than any default-scale official icon (60 % → 144² × 3 = 62 KB) and possibly over a firmware decode buffer; (c) a non-opaque full-canvas image is composited over the firmware's black background anyway. Test with a small (e.g. 144×144) straight-alpha icon to split (a)/(b) from (c).

tar/gzip: the client writes a plain ustar via `ZlibUtils::writeTarHeader` + `writePadded` and gzips with `ZlibUtils::gzipCompress`; formats "%07o"/"%011o"/"%06o" strings are present, i.e. standard octal fields. Our `emulateVendorChecksumBug` flag is a weather-tool artefact; keep it off (default).

## C. What happens on `/upload`, repeated uploads, and the reply fields

Flow (LineOS, CONFIRMED): `UploadControllerUploadHandler` → `UploadController.upload(serialNo, file)` → `UploadServiceIns.uploadConfig()` (`UploadServiceIns.java:184-204`): looks the module up by serial (`ModuleSupervisor.getModule`), computes `serverIp` (`getServerIp`, lines 100-103: the CoreBar **hotspot** IP if the module's `mNetSsid` is empty or equals the CoreBar hotspot, else the CoreBar's Wi-Fi IP), then `UploadService.saveFile(ctx, file, "tgz", "<serial>.tgz", 100 MB, UpdateUI, ".tgz")`. `saveFile` (`UploadService.java:25-55`) writes the multipart body to `<cacheDir>/tgz/<serial lowercased>.tgz`, **deleting any existing file first**, then calls `UpdateUI.process` which does `module.upgrade("http://<serverIp>:8080/tgz/<serial>.tgz")` → `VivoCubeModule.upgrade` → `VCWidgetMain.updateConfig(url)` = QLink message `CMD_UPDATE_CONF` (0x31) whose payload is the URL string (`VCWidgetMain.java:423-462`). `cacheDir` is served statically as `/tgz` (`WebServerConfig.java:15`). The module itself downloads and unpacks the tgz over its Wi-Fi link; the CoreBar never parses it.

Reply semantics (CONFIRMED):

- `{"state":200,"msg":"ok","data":""}` = the module replied to `CMD_UPDATE_CONF` with status byte 0 within 5 s (`UploadServiceIns.java:63-67`, `HttpResult.onSuccess("")`). It does not mean the config has been downloaded or applied. The official client shows "Upload succeeded. Please wait for VivoCube to complete update." (0x100118174).
- `{"state":-1,"msg":"write update command success,update timeout"}` = no reply within 5 s.
- `{"state":N,"msg":"reply error:N"}` with N = module status byte 1…255 (`VCWidgetMain.java:439-441` → `onFailure(property, b, ...)` → `HttpResult.onError(i, msg)`). The official client maps them (0x10011812c-0x100118164): **1 → "VivoCube is currently busy."**, **2 and 4 → "VivoCube is not connected to the network."**, 3 and anything else → "Upload error: <msg>".
- `"data":<integer>` only ever comes from the other route `/upload/zip` (big-screen assets): `uploadZip` returns `HttpResult.onSuccess(Integer count of extracted image files)` (`UploadServiceIns.java:228-230`). It is never produced by `/upload?serialNo=`.
- Other `/upload` errors: "serial required", "module not found"-type exceptions from `getModule`, "hotspotIp ip address is empty", "The file size exceeds the allowed limit" (> 100 MB), "file write fail,…".

Repeated uploads (CONFIRMED from code, consequences HYPOTHESIS): there is no rate limiting, no busy flag and no queue on the CoreBar. Each call overwrites the single `<serial>.tgz` and immediately sends `CMD_UPDATE_CONF` again. `VCWidget.addResultTimeoutTask` uses a 5 s timeout per request and `VCMessage` sequence numbers wrap at 255; nothing serialises updates. Consequences: (1) if the module is still fetching or applying the previous tgz when the next `CMD_UPDATE_CONF` arrives, the busy code 1 is the only protection and is up to the firmware; (2) the file the module is streaming can be deleted/replaced under it (andserver `timeout(10, SECONDS)`), yielding a truncated archive on the module; (3) every accepted update rewrites the module's own flash copy of `com_res<id>/*.bin` (~230 KB per 240×240 opaque pair) — at one upload per 30 s that is ~2 900 rewrites/day on a small SPI flash, which is a wear concern regardless of the black-screen incident.

Black-screen mechanisms backed by code:

- CONFIRMED mechanism, HYPOTHESIS that it fired: `VCWidgetMain.onPropertyReport` (`VCWidgetMain.java:372-385`): whenever the module sends `PR_ID_STATUS_REQ` (property 0, which it does after a reboot/reconnect, i.e. plausibly after applying a config), the CoreBar re-writes the system time **and the cached `mCachedScrState` (property 4) and cached `(mCachedLayerId, mCachedWidgetId)` (property 9)** if they were ever written during this CoreBar process lifetime. Deckhand exposes "Screen Off" (`ContentView.swift:263` → `CoreBarSession.setScreen`, property 4). If screen-off was ever sent, or a `VIVO_CUBE_TOGGLE`/property-9 write named a layer/widget that the newest `config.json` no longer contains, the CoreBar re-applies it after every update and the cube stays dark. Check: read property 4 and 9 (`CoreBarSession.readProperty(deviceId: 256, propertyId: 4 / 9)`); fix: write property 4 = 1 and property 9 = `(1<<16)|101`, or reboot the CoreBar app to clear the cache.
- HYPOTHESIS: corrupted/partial tgz from overlapping updates (above) → firmware fails to load the default layer's icon → black.
- HYPOTHESIS: module flash exhaustion/wear from a few hundred rewrites.
- HYPOTHESIS ruled less likely: image format — all rotation widgets use the same encoder path and parameters as the weather card that displayed.

Duplicate layer ids in `config.json`: nothing on the CoreBar checks them; behaviour is firmware-defined (unknown). Deckhand never emits duplicates (always one layer id 1, widget 101).

## D. How the official client does multiple layers and switching

- Deploy: one tgz containing **all** layers and all widgets of the module, built from the project DB (`buildVivoCubeExtraConfig(bean, buildFiles=true, outTgzPath)`), posted once per "Deploy" click by `ModuleVivoCubeLayer::onClickBtnDeploy` → `HttpUploader::uploadFile(QUrl("http://%1:8080/upload?serialNo=%2"), path, callbacks, timeouts, "file", "config.tgz")` (multipart field `file`, filename `config.tgz`, `application/octet-stream`; timers for "Connection timeout", "Upload stalled (no progress)", "Total upload timeout"). The same data is also saved into the CoreBar gateway config (`canGateway.endpoints[].extraConfig`) so the launcher knows the widget ids.
- Switching: the client never writes property 9 directly (the only `CoreBarApi::writeProperty` call site is deviceId 256 / property 7 = Wi-Fi config at 0x1000fa9fc; `readProperty` sites are property 7, 6 and 5). Layer changes are scene actions: `SceneVivoCubeWidgetConfig::getConfig` builds `VIVO_CUBE_TOGGLE` with `values[{"id":"1","value":"<layerId>"},{"id":"2","value":"<widgetId>"}]` from the chosen layer/widget (`to_string` ×2 at 0x1000a91e8/0x1000a9214; UI label "Set %1 page: %2/%3"). On the CoreBar, `ViVoCubeToggleAction` → `ViVoCubeOperation.toggle(serial, layer, component)` → `CubeConstant.Command.TOGGLE_LAYER` (0x1011) → `VivoCubeModule.writeMessage` → `VCWidgetMain.writeLayerAndWidgetId(layer, widget)` = property **9** (`PR_ID_LAYER_AND_WIDGET_ID`), value `(layer << 16) | widget`, cached and re-sent on status requests. Property 9 is also readable (`readLayerAndWidgetId`), so the current page can be queried. Users can also swipe layers on the module (doc) — the firmware then reports nothing the CoreBar caches, but the cached value will be re-pushed on the next status request.
- Deckhand can drive it directly with `writeProperty(serial, propertyId: 9, value: (layer<<16)|widget)` on deviceId 256 (MODULE_PROPERTY_WRITE act 30201), which is exactly what the CoreBar does on `VIVO_CUBE_TOGGLE`; `widget` should be a widget id that exists in that layer (the client always pairs the layer with one of its own widgets).
- Conclusion: "upload up to 6 layers once, then toggle with property 9" is the intended operating model — CONFIRMED as the official design, HYPOTHESIS that the firmware shows the toggled layer instantly without reload (the client's own scene action relies on it).

## Recommended changes for Deckhand

1. **Canvas** — keep 240×240 for the icon (CONFIRMED to be the official 100 % size). Add a one-off hardware probe mode that pushes opaque 320×320 and 360×360 cards; if one fills the panel, make that the canvas (HYPOTHESIS: panel ≥ 320 px). Do not expect any config key to position or scale the icon; size is the bitmap size (CONFIRMED).
2. **Opaque vs alpha** — keep `allowAlpha: false` as the default (CONFIRMED safe). If alpha is ever wanted, render with `CGImageAlphaInfo.last` (straight alpha) instead of `premultipliedLast` so the bytes match the official encoder (CONFIRMED difference), and test first with a small icon (HYPOTHESIS about size limits).
3. **`config.json`** — current shape is correct (CONFIRMED): `{"defaultLayer":1,"layers":[{"id":1,"items":[{"id":101,"type":1}]}]}`; only `type` and `id` per item, `type` must be 1. For a rotation set, emit one layer per widget: `layers:[{"id":1,"items":[{"id":101,"type":1}]},{"id":2,"items":[{"id":102,"type":1}]},…]`, max 6 layers (CONFIRMED client limit), ids 1…65535.
4. **Rotation strategy** — replace "upload a new tgz every 30 s" with: build one tgz containing all enabled widgets as separate layers, upload once, wait for the module to apply (see 5), then every interval write property 9 = `(layerId<<16)|widgetId` (CONFIRMED mechanism). Re-upload only when the content of a card actually changes (e.g. weather every 10-15 min, music on track change), and never more often than the module needs to finish the previous apply. This also cuts module flash writes by an order of magnitude (HYPOTHESIS on wear, CONFIRMED that every upload rewrites the module files).
5. **Upload handshake** — treat `state:200` as "command accepted", not "applied" (CONFIRMED). Serialise uploads per module, enforce a minimum gap, and after an accepted upload poll `readProperty(9)`/`readProperty(4)` (or at least wait several seconds) before the next command. Map reply states in the UI: 1 busy, 2/4 module not on Wi-Fi, -1 no reply in 5 s (CONFIRMED mapping).
6. **Black-screen recovery** — add a "Recover display" action that reads properties 4 and 9 and, if needed, writes property 4 = 1 and property 9 = `(defaultLayer<<16)|firstWidgetId`; document that the CoreBar re-applies cached values after module status requests (CONFIRMED mechanism). Avoid sending "Screen Off" during a rotation session.
7. **Housekeeping** — the CoreBar lowercases the serial in the cached file name and serves it from `/tgz/`; `getServerIp` requires the module to be on the CoreBar hotspot or the same Wi-Fi — if `/upload` returns "hotspotIp ip address is empty" or state 2/4, the fix is the module's Wi-Fi (`netConfig`), not the image (CONFIRMED).
8. **PROTOCOL.md** — update: bin = LVGL v8 image header (`cf` 4/5, w/h 11-bit) + LE data size, RGB565 byte-swapped; `config.json` items have only `type`/`id`; limits 6×6; property 9 toggling; `/upload` reply semantics and busy codes; the 24 KB "VivoCube_V2_20260728_ota.bin" on GitHub is an STM32 HID blob, not the display firmware.
